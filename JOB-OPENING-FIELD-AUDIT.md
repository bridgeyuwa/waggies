# Job Opening Field Audit

Audit date: 2026-09-24

## Scope and evidence

This audit covers the existing `JobOpening` model, its original table migration, factory, development seeder, Filament resource, careers controller/view, contact handoff, search projection, assistant tool, dashboard work queue, routes, and tests.

The current runtime path is:

```text
job_openings
    ↓
AboutPagesController::careers()
    ↓
resources/views/pages/about/careers.blade.php
    ↓
global ContactController / WhatsApp handoff
```

The current local PostgreSQL database contains **3 job-opening records**. All three have values for title, department, location, employment type, summary, description, and requirements. All three are `open`; two have `published_at` set to the current seed time and one has it null. No record has a `closing_date`. All three contain `application_email = hello@waggies.ng`, while one additionally contains an `application_url`. The local `business_profiles.primary_email` is also `hello@waggies.ng`, establishing that the job email duplicates global business contact data rather than representing a distinct per-job application method. There are **zero** media records associated with `App\\Models\\JobOpening`.

The careers page renders title, department, employment type, location, and summary. It does not render description, requirements, status, dates, sort order, application email, or application URL. The public “Ask about this role” action goes to the existing contact page with `intent=careers` and `source=job-opening`; `ContactContextResolver` does not consume the `job` query parameter, and no job-specific application record or mail workflow exists.

`SearchDocumentSynchronizer` does consume job description and requirements as the searchable body, and department, location, and employment type as keywords. The assistant tool consumes title, department, location, employment type, and summary. These are real runtime consumers even where the careers Blade view does not render the field directly.

## Lifecycle audit

`Draft` is used by the dashboard work queue and is therefore a real admin state. `Open` is used by the public careers query, search projection, and assistant tool. `Closed` and `Archived` have no distinct behavior anywhere in the current application: both are excluded by the same `status = open` predicate, have no separate actions, and have no local records. They are conventional lifecycle labels without a demonstrated Waggies-specific distinction.

The lifecycle should therefore be simplified to:

```text
draft → not publicly listed
open  → publicly listed when published_at is null or due
```

`published_at` is a real scheduled-publication mechanism. A null value means an open role can publish immediately; a future value keeps it out of the public careers query and search projection until due.

`closing_date` is implemented in the current query but has no local data, no test coverage, no public display, and no demonstrated current requirement. Status `draft`/`open` is sufficient for the present product, so the expiry field and its query/index dependencies should be removed rather than retained as an unproven recruitment feature.

## Application method audit

The public careers page does not use either persisted application field. The only action is a link to the existing contact page with a careers intent and a job-opening source. The contact resolver maps that intent to `CAREERS_REQUEST`, but does not read the job ID and does not use a job email or URL. The contact form continues through the established WhatsApp/contact workflow.

The per-job `application_email` is duplicated global business contact data (`BusinessProfile::primary_email`). The one local `application_url` has no consumer. Both fields should be removed. The careers CTA should retain the existing contact handoff while dropping the unused job query parameter so it does not imply a job-specific application record exists.

## Content field audit

`title`, `department`, `location`, `employment_type`, and `summary` are directly part of the public role card and are also used by search and/or the assistant. They remain.

`description` and `requirements` are not currently displayed on the careers page and there is no job detail route. They are nevertheless consumed by the public search projection as the searchable job body. Removing them without replacing that search behavior would change a real public runtime contract. They therefore remain in this surgical cleanup; no child requirement table or additional content abstraction is justified.

## Sort order and media

Manual ordering is real: `AboutPagesController::careers()` orders by `sort_order` before title, the Filament table exposes the order, and the table is reorderable. `sort_order` remains.

No Job Opening media collection, upload, image field, view reference, or media record exists. No media architecture should be added.

## Recommended final contract

The minimal persistent Job Opening contract after cleanup is:

```text
title
department
location
employment_type
summary
description
requirements
status: draft | open
published_at: nullable scheduled publication timestamp
sort_order
created_at
updated_at
```

`id` remains as system identity. `closing_date`, `application_email`, and `application_url` are not part of the final contract.

## Implementation completed

The audit decisions were implemented without changing the careers URL or introducing any new recruitment domain:

1. Migration `2026_09_24_024627_remove_unused_fields_from_job_openings_table` removes `closing_date`, `application_email`, and `application_url`, drops the obsolete closing-date index, and normalizes any legacy `closed`/`archived` values to `draft`.
2. The model, factory/seeder, Filament form/table, and search projection no longer use the removed fields.
3. `JobOpening::open()` and searchability now depend on `status = open` plus a null-or-due `published_at`.
4. The careers contact CTA keeps the existing `careers`/`job-opening` contact handoff and no longer sends an unused `job` query parameter.
5. Focused tests cover two-state publication, future scheduling, the contact handoff, search visibility, admin access, public rendering, and repeatable seeding.

## Removed Fields

| Field | Evidence supporting removal |
| --- | --- |
| `closing_date` | No local record had a value; no public view, application workflow, test, or separate admin action depended on expiry; `draft`/`open` plus `published_at` is sufficient for the current availability contract. Historical creation migrations retain the removed column definitions as immutable schema history. No runtime source retains those fields.

## Publication Model

`draft` records are not public. `open` records are public when `published_at` is null or due. Future `published_at` values remain hidden from the careers page, public search, and the assistant tool. There is no separate closed/archived lifecycle because the current application had no behavior distinguishing those states.

## Application Method

Job openings do not own an application email or URL. The current application method is the existing global contact/WhatsApp handoff from the careers page. The CTA preserves `intent=careers` and `source=job-opening`; it no longer passes an unused job identifier.
